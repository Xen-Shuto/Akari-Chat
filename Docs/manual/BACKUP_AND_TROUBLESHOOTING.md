# データ保全と困ったとき

[詳細マニュアルに戻る](MANUAL.md)

## バックアップする

配布フォルダだけで保管する場合は、**アプリを通常終了してから `Akari-Chat` フォルダ全体を、別の新しいフォルダへコピー**してください。コピー先の既存データを上書きしない形を推奨します。

外部フォルダに置いたモデル・実行ファイルなどは別途保管します。コピー後はフォルダ構成とファイル数・容量などを確認し、元のバックアップは保持してください。

| 対象 | 主な内容 |
| --- | --- |
| `app/characters/` | キャラクター設定、記憶、資料など |
| `app/data/` | 会話DB、設定、添付、履歴、バックアップなど |
| `Models/` | 同梱配置したモデル |
| `app/runtime/` と `llama.cpp/` | 同梱Python・推論エンジンと関連ファイル |

キャラフォルダやログ書き出しだけでは、会話・設定・画像・内部状態をすべて保管できません。会話DBだけのコピーでも、記憶ファイルや画像は保管できません。

Gitで取得したアプリを更新する手順は[利用準備と更新](INSTALLATION.md#更新する)を参照してください。

## 別の場所・PCで使う

1. 元アプリを終了してバックアップします。
2. コピー先が書き込み可能な場所であることを確認します。
3. 内部モデル・エンジンと、外部参照ファイルのパスを確認します。
4. GPUドライバー・ランタイムなどを準備します。
5. 最初は `Start.bat` 内を `set "NO_AUTO_START=Y"` にして起動し、設定を確認します。
6. 必要な外部サービスを再認証します。
7. 元データを保持したまま、会話・画像・記憶が読めるか確認します。

内部のモデル・エンジンパスは設定保存時に相対パスへ揃えます。外部絶対パスは自動で移設先へ置き換えません。

Windowsユーザー向けに暗号化された認証情報は、別PC・別ユーザーでは再登録が必要です。検索索引は再生成可能ですが、会話DBやキャラ原本の代わりにはなりません。

## 動作の確認

「アプリ設定 → 動作の確認」で、アプリ内部ログ・コンソール出力・推論サーバー・ツール要約・生成計測などを確認します。詳細なツール履歴、会話に使う記憶、起動ログも参照できます。

| 見たい内容 | 確認先 |
| --- | --- |
| 会話モデルの起動失敗 | 起動ログ、`app/data/llama-server.log` |
| 検索モデルの問題 | 記憶検索モデルの状態、`app/data/embedding/llama-server.log` |
| 記憶の送信・省略 | 会話に使う記憶の予定と直近の内訳 |
| AIの操作実行 | ツール履歴の状態・結果 |
| 自律・夜間処理 | 自律実行履歴、夜間履歴、AI更新案 |
| 外部送信 | 対象サービスの確認待ち・送信履歴、実サービス側 |

ログ画面の表示クリアは、会話DB・監査履歴・保存ファイルの一括削除ではありません。

## 起動できない・画面が開かない

- コンソールのエラーを確認します。バッチが開いたことだけで起動成功と判断しません。
- 同じアプリが起動済みなら既存の画面を使います。残った `.akari.lock` をむやみに削除する必要はありません。
- ポートが使用中なら、[別ポートでの起動](GETTING_STARTED.md) を試します。
- 同梱ファイルの欠落・書き込み拒否の場合は、配置場所と実際に使われたPythonを確認します。
- 保護機能による拒否が疑われる場合はWindows側の記録を確認します。原因を確かめず保護機能全体を無効にしないでください。

## モデルを起動できない・回答できない

- 会話APIの実効接続先がローカルか外部か確認します。
- GGUF、mmproj、MTP、llama-serverのパスと対応を確認します。
- VRAM/RAM不足ならGPUレイヤー・コンテキスト・モデルサイズを見直します。
- 設定を保存してからモデルを再起動します。
- 外部APIではキー・モデルID・エラー内容・利用枠を確認します。
- 自律処理が実行中なら、完了待ちになっていないか確認します。

サーバーの起動成功だけで、モデルがその会話を正常生成できると断定しないでください。

## 記憶を覚えていない・検索に出ない

1. 正しいルームと保存先を確認します。
2. 草案のままか、本文へ保存済みかを確認します。
3. 直接送信の条件と送信内訳を確認します。
4. 意味検索なら検索モデル・索引・未索引警告・閾値を確認します。
5. 話題選択・休眠・統合などで対象外になっていないか確認します。

直近履歴の上限やエピソードの期間条件もあります。保存しただけで必ず次の回答に出てくるものではありません。

## 画像を送れない・表示できない

画像対応モデル・接続先か、ローカルでは対応mmprojがあるかを確認します。枚数・容量制限、継続添付の選択、ファイルの欠損・退避状態も確認してください。

会話から外した画像は添付管理から戻せます。完全削除済みの画像は画面から復元できません。バックアップのコピーがあるか確認します。

## 保存競合・結果未確認

別タブや外部エディターによる変更があると保存を拒否します。編集中本文を控え、再読込して差分を確認してください。

結果未確認では、同じ操作を繰り返す前に実体・履歴・バックアップ・外部サービスを調べます。「確認済み」は調査したことを記録する操作であり、未完了処理を成功に変えるボタンではありません。

## 設定が壊れている

会話・検索の設定異常では、原本を保持して自動起動を止める経路があります。警告を読み、画面から設定を修正して保存します。保存前データは `app/data/settings_backups/` に残します。

DBや設定を一括削除して初期化する前に、フォルダ全体を保全してください。

## 調査を依頼するとき

発生した操作、時刻、対象機能、エラー本文、モデル名、関係する設定を添えてください。ログや画面には会話・個人情報・接続先・キーなどが含まれる場合があるため、公開前に確認して伏せます。

## 自律行動が始まらない

ルームの会話API接続（ローカルの場合はモデル起動）、対象ルームの保管状態、定期実行の有効化、待機間隔、日次上限、会話待ち、実行中処理、結果未確認、動機判定を確認します。経過時間だけでは実行条件を満たしたとは限りません。日次上限を設けない場合は0にして保存します。研究購読・会話後の記憶処理・夜間整理の文章生成もルームの会話API接続を使います。埋め込み・検索・索引はローカルです。

## Markdownが反映されない

アプリの再起動後も古い表示が残る場合はブラウザを再読み込みします。画像のMarkdown記法がプレースホルダーになるのは仕様です。画像をAIへ渡す場合は添付機能を使います。

## 記録の種類と調査の順番

アプリログは内部の警告/例外、コンソールはプロセスの標準出力、推論サーバーログはモデルの読込/通信、ツール履歴は受付・実行結果、生成計測は待機/生成時間等の記録です。種類の異なる記録を一つの成功判定に混ぜません。

1. 対象ルームと実効接続を確認する。
2. 発生時刻・ジョブ・ツール名で履歴を対応付ける。
3. 成功/失敗/中止/結果未確認を確認する。
4. 保存先や外部サービス側の実体を確認する。
5. 原本を保全してから、必要な最小範囲を再読込・再設定する。

外部APIキーの保存済み表示、モデル準備、索引未更新等を、入力欄の空白だけで判断しないでください。
